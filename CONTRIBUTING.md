# Contribution Guidelines

Hi!

Thanks for your interest in contributing! Whether you're fixing a bug, improving docs, working on new features for the simulation or contributing your own research, your help is appreciated.

These guidelines exist to keep collaboration smooth, respectful and fun for everyone involved.

---

## Ways to Contribute
You don't have to write code to contribute. Here are some great ways to help:

- Reporting Bugs
- Proposing or implementing new features
- Refactoring or improving existing code
- Improving documentation or comments
- Adding or improving tests and test framework
- Sharing sim ides, design feedback and etc...

---

# Getting Started

1. **Fork the repository** and create your branch from `main`

2. **Keep changes focused** one feature or fix per pull request

3. **Write clear commit meesages** that help us understand why changes were made

4. **Test your changes** before submitting

5. **Open a pull request** with a clear description of what you've done

if you're unsure where to start, look for issues labeled `good first issue`, `help wanted`, or `discussion`

---

## Code Style & Quality

Please try to follow the existing style and patterns in the codebase

General expectations:

- Prefer Clarity over cleverness

- Keep functions small and focused where possible

- Avoid unecessary dependencies

- Use consistent naming conventions

---

## Testing

- New features should include tests where reasonable

- we have our own testing framework which can be found in the testing project in the visual studio solution, or the tests dir in the project dir.

- Tests are still pretty lose so I'm not going to be super hard about them but please at least ensure your code builds and that you've tested crucial components if possible. If you need help just ask us. 

If testing is difficult or not applicable, explain why in your pull request. 

---

## Documentation matters.

If your change effects behavior, or usage

- Update the README or relevant docs

- Add doc comments on functions and comment where futer readers might get confused

- Keep examples minimal but accurate

---

## Pull Request Guidelines

a good pull request:

- has a descriptive title

- explains what changed and why

- links to relevant issues or discussion and documentation

- notes any breaking changes or limitations

Draft PRs are welcome if you want early feedback.

---

## Bug Reports

When reporting a bug, please include:

- A clear description of the problem

- Steps to reproduce

- Expected vs actual behavior

- Relevant logs, screenshots, or stack traces

- your environment (OS, compiler/runtime, versions, etc...)

the more context you provide the easier it is to help. 

---

## Feature Requests

Feature ideas are welcome!

Please include:

- the problem you're trying to solve.

- why this feature would be useful

- any prior art or references

- possible implementation ideas (optional)

Not every idea will be accepted, but all thoughtful suggestions are appreciated.
